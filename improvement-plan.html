Portfoliarr audit and roadmap

A full audit of version 1.3, written 5 October 2026. It answers one question: can this app become the self-hosted leader in investment tracking? The answer is not yet. This page says why, and what to do about it.

The verdict

For one job, the app works well. A Canadian or US investor can log stock and ETF buys and sells and see value, gain, a value chart, realized profit and allocation. The data layer fails honestly. Ownership checks are solid. The suite has about 1,240 tests across 75 files.

For the rest of the world, it does not do the job. Portfolio views are fixed to Canadian dollars. A holding in any other currency is dropped from the totals, the chart, the allocation and the realized gains, and the summary blames Yahoo for a pricing failure that never happened.

Two math problems can mislead any investor, in any country. Stock splits are not handled at all, and the app charts Yahoo's split and dividend adjusted prices while the ledger stores raw traded prices. Both need fixing before new features matter.

The plan follows one order: make the numbers true, then make the app worldwide, then make self-hosting trustworthy, then add the extras that win comparisons.

What is solid

  • Failed quotes become a dash or null. The app never fakes a 1 to 1 exchange rate.
  • Every portfolio route checks the session user. A foreign portfolio ID reads as a 404, not as another ledger.
  • No SQL injection. Rendering is XSS-safe. Passwords use scrypt. The session secret is stable across restarts.
  • Where the accounting exists it is careful: average-cost replay, fees split per share, short symmetry, per-transaction frozen FX, TWR with flows removed.
  • Operations are covered: Docker healthcheck, volume persistence, non-root serving, request-ID logging, and a CI gate before the image publishes.
  • The Android client adds biometric unlock, in-app updates and two home-screen widgets. No other self-hosted tracker this size has that.

D. Resilience and scale

  • Yahoo is the only data source. There are no retries, no backoff and no second provider. One block or rate limit takes out quotes, charts, FX and search together (market_data.py:25).
  • One cold dashboard load makes about 58 + 11 per holding + 2 per watchlist item Yahoo calls. Nine chart periods preload at once (static/js/main.js:1687).
  • One process with eight threads, SQLite and memory caches serves a household well. A public multi-tenant service would need a different design. Your goal is one instance per person, so this stays a low priority.

The roadmap

Four phases, ordered by dependency. Phase 0 comes first because later phases build on the same replay code.

  1. 0Make the numbers true: fix the math, then add splits, cash and dividends.start here
  2. 1Worldwide use: configurable currency, per-day FX, timezone, formatting.
  3. 2Trust and operations: backup, export, security, Yahoo resilience, reproducible builds.
  4. 3Extras: reports, imports, targets, integrations.

Phase 0: make the numbers true

Sprint 0A fixes bugs and needs no schema change. About two to three days with tests. Each fix lists the tests that must fail first, then pass.

FixWhat changesTests
1. Adjusted prices leak into charts and auto-fill Pass auto_adjust=False in get_history (market_data.py:937), get_price_on (market_data.py:1059) and get_fx_rate_on. Yahoo then returns the raw close, which matches the raw prices stored in the ledger. A known split symbol returns its raw close from history and auto-fill. A chart series equals the raw closes.
2. Future-dated trades count today Add one _today_iso() helper. Summary, realized, allocation and the position card fold only rows dated today or earlier. The ledger still shows the row and the warning stays. A future buy is not in value, cost or day change. A future sell is not realized. A trade dated today counts. The ledger still lists the future row.
3. Editing a trade replaces its FX rate In PUT /api/transactions/<id> (app.py:3551), recompute fx_rate only when the date changes. A same-date edit keeps the stored rate even when a fake history reply returns another rate. A date change recomputes it. A failed lookup follows the existing fallback order.
4. Sell rows show a gain that was never earned Blank the per-transaction Total Gain cell on sell rows. The group row and Closed sales keep showing realized profit. A sell detail cell shows a dash. Buy rows do not change.
5. The cost basis label is wrong Rename "Cost basis" to "Net invested" in the summary and chart legend, and add a tooltip with the exact meaning. Both strings are pinned by a UI test.
6. One bad row hides the realized total Keep the null on the bad row. The total sums the rated rows and returns degraded_count and partial: true. The page shows a partial marker. Mixed rated and unrated rows produce a partial total and the marker. All-rated rows behave as before.
7. The test gate has holes Stop db.init() from touching the real database when tests import the app. Add py-mini-racer to a dev requirements file so the JavaScript tests run in CI. The suite runs with no skipped JavaScript tests.

Sprint 0B changes the schema. About one to two weeks. Run the items in this order.

  1. Stock splits (roadmap item 46). Add a SPLIT transaction type. Fold it through the summary, the history walk, the average cost replay, the realized replay and the position card.
  2. Cash (roadmap item 5). Track a cash balance with deposit and withdrawal actions. Once cash exists, buys and sells settle against it and TWR uses deposits and withdrawals as its flows.
  3. Dividends (roadmap item 6). Add a DIVIDEND type. Cash income counts in total return. An optional DRIP logs a linked buy.

Phase 1: worldwide use

  1. Configurable base currency (extend roadmap item 8). Each person picks their display currency. Any Yahoo FX pair converts. A non-USD/CAD holding converts or visibly degrades with a reason, and never leaves the total without a plain-language note.
  2. Per-day historical FX (part of item 8). The chart converts each past day at that day's rate instead of one live rate.
  3. User timezone (new item 61). Remove the Toronto pin from "today" logic, future-date warnings and the 1D chart.
  4. Locale formatting (new item 62). Use Intl for numbers, dates and currency symbols. Remove the hardcoded dollar sign and the en-US locale.
  5. Translation decision. Full UI translation stays out of scope unless you ask for it. Timezone, currency and formatting come first and cover most of the need.

Phase 2: trust and operations

  1. Backup and restore (roadmap item 47), CSV export (roadmap item 2), SQLite WAL mode and a documented snapshot procedure.
  2. Security hardening (new item 63). A reverse proxy and TLS guide, a Secure cookie and ProxyFix, CSRF tokens on the auth forms, a request body size cap, rate limits on Yahoo routes, the dev server bound to localhost, and a LICENSE file. The "any user can delete any user" rule stays for a family LAN and moves behind a role check when remote access is on.
  3. Yahoo resilience (new item 64). Retries, backoff, a circuit breaker, a smaller dashboard preload and a second FX source.
  4. Reproducible builds and test gate (new item 65). Pin transitive dependencies, remove pytest from the production image, make the JavaScript tests run in CI, and stop tests from touching the real database.

Phase 3: extras

This is a menu, not a sequence. Pick items when phase 0 and 1 are done.

  • Full import with sells and fees, plus broker CSV maps (roadmap item 48) and an export round trip.
  • Reports: annual realized (36), calendar returns (40), contribution to return (42), dividend income, and an optional FIFO or specific-lot method.
  • Targets and rebalancing (28, 50), watchlist target prices (33), server-side preferences (32).
  • Small UX items already on the roadmap: quick-watch star (34), holdings age (30), volume bars (56), pull-to-refresh and share (35), search and stats caches (11, 12).
  • New candidates: a read-only public API with scoped tokens (66), alerts and notifications (67), and a decision on manual assets such as real estate, private holdings and liabilities (68).
  • An iOS client or a PWA. Both wait on HTTPS, which phase 2 delivers.

Two product choices

These are the recommended answers. Say so if you want them changed.

sell rows

A sell detail row shows a dash instead of a per-sale realized number. Realized profit stays in the group row and the Closed sales table.

realized total

The total becomes the sum of the rated rows, marked partial, instead of becoming null when one row is bad.

  3. Implement the fixes until the tests pass.
