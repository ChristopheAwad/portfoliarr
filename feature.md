## Agreed product behavior

1. Portfolios are independent named groups of transactions. There is no combined/all-portfolios view, broker-account hierarchy, transaction-moving action, or copied starter trades. Holdings, summary, chart, allocation, ledger, and closed sales refer to the selected portfolio. The market overview, volume leaders, ticker search, stock quotes/history, and one watchlist remain global. No new user accounts or authentication.
2. On upgrade, create a default portfolio named `Main` and move every existing transaction into it without changing the transaction ID or any other stored fact. Keep the old watchlist global. A new database also starts with one empty `Main`. Any portfolio, including `Main`, may be renamed or deleted after another exists; at least one portfolio must remain.
3. The dashboard and ledger each have a compact portfolio selector beside the portfolio/ledger heading. Preferences has controls to create, rename, move up, move down, and delete portfolios. A new portfolio is empty. Order is explicit, not alphabetical or drag-and-drop. Trim names and enforce nonempty, case-insensitively unique names. Choose and document a fixed, reasonable maximum name length (for example 60 Unicode characters); apply the same rule at the API and database boundaries. Display names as text, never HTML.
4. The active portfolio is a saved choice in this browser, shared across its tabs and all pages. Other devices retain their own choice. Changes in one tab update other open tabs immediately. Missing, corrupt, or deleted saved IDs fall back deterministically to the first portfolio in display order and replace the bad stored choice. After deleting the active portfolio, select a remaining one. The portfolio name is visible at the ledger transaction form before saving. Privacy masking stays browser-wide across portfolios; existing theme, sort, display currency, and allocation preferences also retain their current behavior.
5. The stock page stays a global security page with the global watchlist button. Its Log Transaction button opens the ledger's existing ticker-prefilled form in the currently selected portfolio. Links from the market overview, search, and ledger to stock detail do not change global quotes or watchlist ownership.
6. A portfolio change clears any unsaved transaction form, edit mode, quick-sell preparation, and stale import preview/commit permission, including when the switch came from another browser tab. The paste text may remain so the user can preview again. Preview writes nothing; commit reparses the original text and writes only to the explicitly selected destination. A switch after preview requires a fresh preview. A change during an in-flight save must not silently redirect that save to a different portfolio; capture the destination at submit, guard the UI response, and require review before any new submit.
7. Deletion of a populated portfolio deletes all its transactions in one database transaction after the user types its name for confirmation. Verify the confirmation on the server as well as in the UI. Do not delete or alter the shared watchlist. Refuse deletion of the last portfolio. A missing/deleted portfolio cannot accept reads or writes as if it were `Main`.

## API and persistence contract for implementation

- Create `portfolios(id INTEGER PRIMARY KEY, name TEXT NOT NULL, sort_order INTEGER NOT NULL)` with a case-insensitive unique index on names and a nonempty/length validation path; keep IDs stable when names or order change. Expose `GET /api/portfolios` in display order, `POST /api/portfolios` with `{name}`, `PATCH /api/portfolios/<id>` with `{name}`, `PATCH /api/portfolios/<id>/move` with `{direction: "up"|"down"}`, and `DELETE /api/portfolios/<id>` with `{name}` for typed confirmation. Reply with the stored id/name/order for creates, renames, and moves; deletion replies 204. Specify consistent 400 for invalid shapes/names/directions, 404 for missing IDs, and 409 for duplicate names, deletion of the last portfolio, wrong confirmation, and out-of-range moves. A failed mutation must not partially change order, membership, or transaction data.
- Add `portfolio_id INTEGER NOT NULL REFERENCES portfolios(id)` to the transactions table. SQLite cannot add this constraint to legacy rows in place: after creating `Main` and preserving the existing `fx_rate`/`fee` migrations, rebuild the table inside one SQLite transaction if the column is missing, copy the old rows with unchanged IDs/facts and `Main`'s ID, then replace the old table. On fresh databases create the final schema directly. Enable SQLite foreign keys on every connection and explicitly perform portfolio-and-transaction deletion atomically, either with tested cascade or ordered deletes. Add portfolio-scoped query indexes if useful. `db.init()` is idempotent. Do not change immutable-trade math, currency semantics, or the global watchlist schema.
- Every portfolio-dependent browser request includes an explicit positive integer `portfolio_id` query parameter: `/api/portfolio/summary`, `/api/portfolio/history`, `/api/portfolio/allocation`, `/api/portfolio/realized`, `GET/POST /api/transactions`, `PUT/DELETE /api/transactions/<id>`, `DELETE /api/transactions/ticker/<symbol>`, and both import routes. Keep request bodies' existing transaction/import fields intact. Validate the parameter centrally before any market fetch or write: malformed/zero/negative IDs get 400, unknown IDs get 404. Existing API callers and older tests without a parameter resolve to the first portfolio in stored display order (initially `Main`); do not use this compatibility behavior in the new frontend. This fallback must never apply to an explicit invalid or deleted ID.
- Scope all DB transaction list, insert, fetch-by-id, edit, single delete, and bulk ticker delete operations by portfolio ID. A transaction ID owned by another portfolio returns 404 for edit/delete and cannot be modified. Pass the scoped transaction list to the existing summary, history/TWR, allocation, ledger grouping, and realized replay code, so each calculation keeps its current accounting behavior. Imports use one captured validated destination on preview and commit. Return `portfolio_id` in stored transaction facts and mutation responses for clear ownership. Keep global `GET/POST/DELETE /api/watchlist` and stock/market/search endpoints independent of portfolio ID.
- Centralize browser portfolio loading, saved selection, change notification, and URL parameter building in `static/js/common.js`. Keep the active ID in `localStorage`; use its `storage` event for other tabs and a same-tab notification for the page that made the change. Do not store the server's portfolio list as the source of truth in browser storage. Handle server-side rename, reorder, and delete by refreshing that list and resolving stale choices. Do not use page-level `setInterval`; use existing `setupAutoRefresh` for polling.
- Reuse the current dashboard chart, but ensure its cache and outstanding request generation include portfolio identity. A slow reply or a prefetched history from portfolio A must never populate portfolio B's chart, hover cost, return readout, or cache entry. Apply the same request-generation/identity guard to summary, allocation, ledger, and realized fetches; clear old portfolio-specific rows and numbers on switch before new data arrives. Shared market and watchlist refreshes remain global. Preserve the current `index_values`/`twrr_pct` null and short-array contract and the shared chart's stock-page behavior.
- Add route-boundary audit logs for portfolio create/rename/move/delete with request ID and portfolio ID but no transaction amounts, request body, or portfolio names. Keep error catches at the route boundary and DB helpers free of Flask/market dependencies. Do not change Android business logic: its WebView reads the same browser selection and server API.
